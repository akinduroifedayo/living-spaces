## 1. Definition and promise

**“An open canvas for your bots that live in Hermes.”** A Space is a persistent surface the user and their bot share: any dashboard, data display, mini app, game, document or larger multi-view application. The bot is the trusted author; the canvas is its surface. The sandbox protects Desktop and other canvases, not the user from their bot.[1][2]
Build and change it in normal Hermes chat. Open it from chat or the Spaces tab, use it, return later, ask the bot to evolve it, and keep it current without starting over. No separate builder conversation or code-pasting workflow.
What the user enters persists. Refresh never overwrites their notes, choices or other user-owned fields. Saved means saved. Chat, canvas and upkeep operate on the same authoritative records; code revisions and data recovery remain separate.
This brings a familiar persistent, chat-built workspace capability to Hermes; do not claim novelty over Grok Pages or Muse Spaces. No GBrain or other non-stock integration is required. Demonstrations use public, generic content, never private account material.[1][5]
The product bet is repeat use and evolution, not artifact creation counts: validate create → use → return → change → upkeep. Repeated abandonment or maintenance that drives users back to external software would challenge the bet.

## 2. What the plugin provides

- **Hosting:** a discoverable Desktop home, stable Space identity and bot attribution, multi-file projects, assets, libraries, navigation and a working Open Space action.
- **Persistence:** durable records and preferences, live changes from chat/upkeep, conflict handling, coherent batch writes, project history, restore and scoped diagnostics for repair.
- **Upkeep:** a link to ordinary native Hermes cron, not another scheduler. The Upkeep panel reads native prompt, cadence/timezone, next run, current state and executions; Pause, Resume, Run now and Remove act on that native job. Native executions remain the history of agent runs.[2][6]
- **Isolation:** a canvas-bound bridge and opaque frame keep generated JavaScript out of Desktop internals, host credentials, arbitrary files and other canvases. Native bot actions use native authority, not a raw privileged bridge.[4]
- **Strong defaults:** accessible controls, honest save/failure/freshness states, recoverable updates, optional behaviour helpers, and ambitious design guidance. Defaults accelerate authorship; they do not define a house style or a complexity ceiling.

## 3. The only limits — and why

**Test every limit:** does Hermes impose it on the bot or its own chat widgets? If not, name its concrete isolation, data-integrity or resource reason here or remove it. A missing helper, aesthetic preference or old release boundary is not a safety reason.[1][4]

| Boundary | Reason and consequence |
|---|---|
| Native authority stays native | Hermes owns tool approvals, credentials, cron execution policy and device/OS prompts. A canvas request cannot bypass them; the plugin adds no second per-tool, per-site, per-device or schedule consent system. Raw registry dispatch alone is not proof of native policy enforcement. |
| Canvas/host separation | Guest code cannot read Desktop's DOM, credentials, arbitrary filesystem or another canvas's store. Bind operations to the actual backend/profile, Space and live session; reject spoofed identity, path escape and stale-session delivery. Native-authorized bot reads/writes remain possible. |
| Internet switch | On by default, controlled outside the canvas; guest code cannot switch itself back on. Off stops supported canvas internet paths, not the bot's normal tools. Previously delivered data cannot be recalled. WebRTC remains a disclosed exception: Off is not a promise of zero outbound data. |
| Data integrity | Preserve user/source ownership, stale-write conflicts, atomic operations and recoverable revision/migration changes. Refuse ambiguous mutation targets. These prevent lost work, not creative output. Code restore never silently rolls back user data. |
| Automatic model spend | Guest `space.refresh()` runs only the cheap no-model feed handler; an agent handler is refused before dispatch. Mount/timer/retry refresh must not turn into agent upkeep. Host Refresh now, native chat and native cron may run the agent. This limit is explicitly accepted by Ife.[2] |
| Finite resources | Generous, visible payload/storage/execution limits protect Desktop and other canvases. Report the actual limit and recovery route, never silently truncate. Per-file/per-revision budgets are not a total retained-storage guarantee. No arbitrary app-size tier or plugin-only prompt cap. |

The current mediated network implementation adds public-address and transport checks for host isolation. They describe that adapter, not a new restriction on the bot or a settled permanent open-frame policy; section 8 addresses the unresolved credential issue. Browser/runtime capability limits must be stated accurately, not dressed up as product bans.[2][4]

## 4. Capabilities

**Internet.** On by default per Space, with an Off switch. The intended turn-in capability is ordinary web content **open in the frame**—images, fonts, CDN libraries, embeds and live connections as Hermes's own widgets permit—plus `space.net.fetch` for mediated API calls. Do not add site lists or approval panels.[1][2]
**Observed implementation, not the target:** the inspected branch still describes mediated public HTTPS, with direct frame networking blocked; it does not prove CDN, embeds or WebSocket support. The latest instruction requires evidence on ambient backend-header exposure before shipping open-frame default-on. Neither “mediated forever” nor “open-frame already safe/shipped” is settled; see the first open decision.[2][4][7]
Turning Off must have an intelligible fallback: retain useful saved/local content, label stale data or samples, and never silently present fixtures as live. Do not claim complete egress prevention; explain the WebRTC exception in accessible host documentation/copy.

**Files and libraries by reference.** The bot can take generated images, fonts, scripts, libraries and other files it can legitimately access and add them to the Space by reference, without pasting bytes/base64 into its response. Import creates durable project assets: reopening/restarting and restoring the revision must not depend on a temporary source path. Preserve containment, clear missing-file/size errors and native file/tool policy; do not give guest code arbitrary host-file access or add a new consent layer.[1][2]
Any framework or plain JS is valid; compiled browser-compatible output, custom CSS, bundled or self-vendored libraries are welcome. The shelf is convenient, not exhaustive. Native build/install rules still govern the bot's actual tools. Package automation, if added, is optional—not another mandatory dependency-approval system.[4][6]

**A canvas asks its bot.** A control such as “Explain this” or “Change this view” sends the canvas context and request through a real native bot turn, addressed to its maintaining bot/session, not whichever chat happens to be active. The bot uses its normal tools and skills under Hermes's rules and can update the same Space. Acknowledged/submitted is not completed; unavailable, busy, failed and completed outcomes must be honest. No per-tool plugin grant. The exact cost guard is open, not a license to turn guest refresh into model work.[1][2][4]
Device and connected-tool capabilities follow that same native path. Do not advertise direct frame camera, microphone or location access merely because Hermes has a tool or an OS prompt; unsupported native seams are concrete implementation gaps, not reasons to invent switches.[4]

**Upkeep.** A user asks in chat; the bot creates an ordinary Hermes cron job with its normal native tools, skills and policies. No plugin approval, copied schedule state or mirrored agent-execution ledger. Display when work uses model calls. Host Refresh now runs the linked agent job or a native one-off if none is linked; feed refresh remains a cheap alternative. The panel shows the job that actually runs, even if the manifest later changes.[2][6]
Archive pauses linked jobs and pending Refresh-now one-shots; unarchive does not resume them. Delete removes future jobs and links. Report native pause/remove failure rather than claiming success. Already-running work may finish under native semantics; pause/remove is not cancellation of completed effects. Native catch-up and runtime availability govern missed work; no always-on cloud service is promised.[2]

## 5. Design: no house style inside a canvas

The host is a quiet frame around the bot's work. Show authorship, useful status and controls without repeated warnings, empty “Not reported” metadata or an approval-dashboard feel.[1][3]
The kit is an optional toolbox; its CSS is one optional look. No mandatory Preact, JSX ban, component tree, palette, card grid or fixed page layout. The user's design skill and requested style take precedence.
Encourage a distinct concept, typography, colour, depth, imagery/illustration, authored motion and data visualisation suited to the task. Premium means a coherent useful experience, not obligatory ornament. Preserve keyboard access, focus, contrast, reduced motion, responsive layouts and clear empty/loading/error/conflict states.[3]
Qualify actual chat-built outputs after the guidance changes, not just hand-authored references. The showcase should span a dashboard, a mini app/game, and something neither—such as a reading experience, document or live board—with genuinely different identities and imagery where it helps.[3]

## 8. Open decisions for Ife

1. **Open-frame internet and ambient credentials — first.** Ife's rule is Hermes-widget parity, including no extra home-network block in open mode. But current inspected shipping-path evidence is mediated public HTTPS, not a verified open frame without a home-network block. Desktop source attaches configured backend headers by URL; Forge must establish whether Spaces and native widgets actually receive them, which URLs are affected, and whether a credential-free session is reachable. Recommendation: preserve the open-frame target and fix any concrete credential exposure, not recreate per-site consent. If exposure is confirmed, Ife decides the shipping stance; neither unqualified openness nor permanent mediation is silently accepted.[1][2][4]
2. **Every bot's canvases?** Today the tab reads the active backend/profile's store; owner labels do not prove cross-bot discovery. Should it aggregate every bot's canvases? Recommendation: yes, with explicit owner routing and existing store isolation preserved—not a flattened global store.[4]
3. **Private data with Internet On.** How should the host tell the user that private tool/file data displayed on a canvas can leave it? Recommendation: concise, persistent Internet status and contextual explanation when private data is brought in, not another permission system. Final wording/trigger remains open; public-only demos do not resolve this product question.[1][4]
4. **Canvas-to-bot cost guard.** Does a user-facing bot request need a guard beyond native submission behaviour? Recommendation: reuse native request/busy feedback and deduplication, with no added approval screen; qualify automatic/repeated submissions before choosing more. Keep the accepted feed-only guest-refresh boundary regardless. Any additional guard remains proposed, not a settled limit.[1][4]
